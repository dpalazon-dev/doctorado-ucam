# Workflow PRE/P1/P2: definitions, gates, and revisions

Status: **Accepted**, ADR-017, 2026-10-02. Canonical detail for Workflow v0.1; CONTRACTS retains DTOs/signatures at contractVersion=1. This documentation decision does not claim implementation or executable gates.

[PRE.v1.json](phase-definitions/PRE.v1.json), [P1.v1.json](phase-definitions/P1.v1.json), and [P2.v1.json](phase-definitions/P2.v1.json) are canonical, immutable version 1 payloads. The implementation may embed them at build time. Changing their content requires a new version and preserves the versions pinned by each Paper; do not generate different templates at runtime.

## Definitions and answers

Version=1 is canonical; pin all three definitions when initializing processing. The JSON contains exactly the fields in PhaseDefinitionDto ([CONTRACTS.md](CONTRACTS.md)). The hash is the lowercase hexadecimal SHA-256 of the JSON without definitionHash: UTF-8 without BOM, no whitespace, keys recursively sorted in lexicographic order, arrays retaining their order, and JSON strings without forced ASCII escaping. No text, rule, or allowedRes value changes within an approved version.

PRE now has **six visible outputs**, not five: the five existing questions plus review_type. The sixth output uses `structuredValue={reviewType: ReviewType}`. Known types use ANSWERED; an unknown type uses UNKNOWN with a non-empty explanation. Saving validates the closed object, and evaluation requires equality with the current Paper.reviewType. It does not modify Paper or reinterpret its type from prose. If metadata changes, the answer retains its previous value and the gate returns invalid until the user confirms it again. An imported default of unknown does not create this answer. The PRE label is “Confirmed bibliographic type.” P1.review_type is labelled “Review focus according to the source”: it characterizes how the source presents the review and the methodology the text declares, with a textual answer; it does not create a second bibliographic editor or update Paper.reviewType ([DOMAIN.md](DOMAIN.md); [CONTRACTS.md](CONTRACTS.md)).

allowedResolutions includes PENDING where a draft may be saved; PENDING always blocks the gate. The exact matrices are in the JSON. Rationale: purpose/uncertainty/depth and the P1 decision are explicit decisions of their own (ANSWERED); the baseline allows UNKNOWN/NA; the expected outcome allows exploratory UNKNOWN. P1 allows UNKNOWN about the source; NA is allowed only for out-of-scope, bibliographic cut-off, and optional organization. P2 allows UNKNOWN and NA for reviews whose relevance may be absent; synthesis allows UNKNOWN but not NA; candidates require an explicit ANSWERED decision with either a selection or a justified absence. These are not scientific quality controls or quotas.

Common rules: a textual ANSWERED requires non-empty answerText. UNKNOWN/NA requires an explanation; do not duplicate it in answerText. PRE.review_type and P1.relevance_decision are processed from their valid structured values, without redundant prose. P1 ANSWERED requires both enums; UNKNOWN/NA are not allowed. PENDING permits structuredValue=null; a partial object is rejected as invalid rather than filled with invented values. Textual PRE/P1 outputs use structuredValue=null except for those two exceptions. An absent/PENDING optional output has no completeness requirement; any saved value remains part of the snapshot and invalidation.

Normalization before validation, persistence, and no-op comparison: answerText/explanation replace CRLF and CR with LF and trim outer whitespace; they do not collapse internal spaces or change Unicode/case. Empty answerText is stored as ""; empty explanation as null, unless the resolution requires it. ID/enum strings are not repaired; they are validated. Objects are closed; unknown keys, non-finite values, and values beyond limits are rejected without truncation. UUID sets use lexicographic order; duplicates are rejected. Content JSON is not semantically reordered except for declared sets. No-op equality compares these four canonical values, not timestamps/revisions.

## Declarative rules and P2 evidence

completionRules lists required handlers; **it is not a blind conjunction of their names**. Every requiredOutput must pass its handler. PRE.answerProcessed validates its six answers and the non-empty title derived from Paper; paperHasActiveDocument requires a current, available ACTIVE Document. Bibliographic dependencies do not create synthetic answers. P1 uses answerProcessed for textual outputs and p1DecisionProcessed for the decision, with all three valid branches.

P2 uses p2ArtifactPresent by key after validating the resolution. For its first six outputs, structuredValue is `{itemIds: UUID[], relationIds: UUID[]}`: it represents explicit links from an answer to existing entities/relations, not substitute aggregate text. References are preserved in the versioned PhaseAnswer and validated against canonical associations in the same TX. Missing IDs, incompatible types, archived entities used as current evidence, or a missing link to the Paper make the answer invalid. Saving the answer never creates IDs.

| P2 key | Admissible answer artifacts | When no relevant artifacts exist |
|---|---|---|
| main_questions_processed | itemIds of Questions associated with the Paper; empty relationIds | Non-empty explanation of absence/irrelevance or uncertainty |
| field_synthesis | itemIds of Insights associated with the Paper that retain the synthesis; empty relationIds | Explained UNKNOWN, or ANSWERED that explicitly records why there is no material from which to produce a synthesis; no synthesis prose without an entity |
| relevant_concepts_reviewed | itemIds of Concepts associated with the Paper or linked from its items; empty relationIds | Explanation of absence/irrelevance or uncertainty |
| meaningful_relations_reviewed | relationIds whose endpoints are linked to the Paper; empty itemIds | Explanation of absence/irrelevance or uncertainty |
| contradictions_reviewed | relationIds of contradicts with endpoints linked to the Paper; empty itemIds | Non-empty explanation of absence or uncertainty |
| references_classified | itemIds of References associated with the Paper, with persisted state and reason; empty relationIds | Explanation of absence/irrelevance or uncertainty |

No row requires a minimum number of artifacts. With empty arrays, explanation is the sole canonical justification for absence (including ANSWERED); UNKNOWN/NA also follows the common rule. NA uses empty arrays. With non-empty arrays, the summary identifies what was reviewed and the entities retain the content. High confidence, no pending provenance, and epistemic validation are not required. Insight, an existing type, backs the synthesis. [DOMAIN.md](DOMAIN.md) requires queryable entities/relations and justified absence; [DOMAIN.md](DOMAIN.md) allows Insight and uncertainty without fabricating evidence. This clarification prevents six narrative fields from becoming a requirement for a complete concept map.

For p3_candidates_or_justification, the pair `p2ArtifactPresent` / `p2NoCandidatesJustified` is a **closed, exclusive alternative for that key**, without a new DTO operator. The other p2ArtifactPresent handlers remain required for every preceding key. OR must not hide integrity errors or unavailability:

| Canonical candidates | Canonical justification | p2ArtifactPresent | p2NoCandidatesJustified | Result |
|---|---|---|---|---|
| >0, associated Claims/Questions, non-empty rationale, priority null or 1..5 | null | true | false | passes |
| 0 | non-empty text | false | true | passes |
| 0 | null/empty | false | false | pending/invalid |
| >0 valid | absence text | invalid | invalid | blocked |
| Inconsistent IDs/types/attributes | any | invalid | invalid | blocked |
| Required resolver/capability absent | any | not evaluated | not evaluated | UnsupportedCapability |

Structured projection of this output: `{candidates:[{itemId,priority,rationale}],candidateCount,noCandidatesJustification}`. paper_items associations are the single authority for selection/priority/rationale; the object is a checked projection, never a second editable selection. The only absence justification is stored in `phase_answers(P2,p3_candidates_or_justification).structuredValue.noCandidatesJustification`, not another row/table/field or the explanation field. The output's explanation is null; optional text does not control selection or absence. The service generates and verifies the candidates and candidateCount projection.

T06.setP3Candidate updates the association and output in the same UoW. A real change to its projection increments PhaseAnswer.revision/updatedAt and the P2 clock. Zero candidates requires a justification; more than zero requires null. Production enables savePhaseAnswer for this key after T07; with zero items/candidates it records the justification without a fictitious itemId. candidates/count must match the DB projection, and saving does not change the selection. UNKNOWN/NA do not close this decision. set/save/summary/gate read one persisted justification. PENDING allows an incomplete decision.

T04 stores/pins/reads the definition and P2 answers, and opens a PhaseRecord after accepted continue. set/getP3Candidate remain UnsupportedCapability until the real T06 use cases exist; all production P2 save/evaluate/advance remain UnsupportedCapability until T07 supplies complete resolvers (ADR-023). Do not query future tables or report a complete gate from empty arrays. T05/T07 supply capture/persistence and T06 supplies resolvers against the pinned definition. Final P2 acceptance waits for T07 and all its capabilities: any missing required handler yields UnsupportedCapability even with empty lists or justified absence.

## Snapshot, revisions, and no-op

Canonical internal snapshot: `{snapshotVersion:1,paperId,phaseCode,definitionVersion,definitionHash,answers,inputs,artifacts}`. answers contains every declared key, including optional ones, by questionKey; each entry retains answerText/structuredValue/resolution/explanation/revision. A missing row is represented as empty PENDING, revision=0. It excludes updatedAt, evaluatedAt, phaseRevision, phase state, activePhase, lifecycle, and timestamps: navigation/completion does not change gate content. Hash uses the same canonicalization/SHA-256 as the definition. Save the complete accepted snapshot, not only its hash ([DATA.md](DATA.md)).

PRE inputs: `{title,reviewType,document:{id,status,sha256,available}}`. P1 inputs: `{preAcceptedGateSnapshotHash,preDefinitionHash,document:{id,status,sha256,available}}`. P2 inputs: `{p1AcceptedGateSnapshotHash,p1DefinitionHash,readingDecision,document:{id,status,sha256,available}}`, with readingDecision=continue. The document is the current registered Paper document in all three phases; its live availability is not replaced by the prerequisite's historical snapshot.

**Forward enablement and completion (R1):** P1 requires PRE COMPLETED, an accepted snapshot, and a currently satisfied PRE gate; P2 requires the same from P1, the entire prior chain to remain current, and an accepted readingDecision=continue. A sufficient gate in IN_PROGRESS is not an acceptance. This policy governs every touch that initializes or activates a later phase and advance that completes it; touch never accepts the prerequisite or produces NEW→ACTIVE. NEEDS_REVIEW requires the prerequisite to be reconfirmed before continuing/completing. Reading already-started data remains available without deleting or implicitly accepting it; returning to an earlier phase preserves content. Forward activation, even when data already exists, and completion still require the current accepted chain. Saving continue without accepting P1 does not enable a new P2.

**Live document access (R2):** evaluate/advance for PRE/P1/P2 obtains proof of access and retains a verified handle to the current document before the TX, through the document port and ownership guards. Inside the consistent read or short IMMEDIATE TX, it revalidates Paper.documentId, the registered Document identity/status/hash, and agreement with the proof. If the DB changes between proof and TX, the operation is rejected without using stale proof. The handle/guards are retained until the check/commit ends. The concrete ABI is fixed after T03; a PDF up to 500 MiB is not read or hashed under DbActor/TX. A missing/inaccessible document blocks the gate and produces available=false in the current snapshot while preserving the accepted one; advance changes no phase/lifecycle and writes no success receipt. External disappearance does not fabricate a clock increment; a DB Document change does renew revisions/invalidate in its UoW. The design does not promise to detect every external change or tolerate hardware failure.

PRE/P1 artifacts are empty; their concrete dependencies are in inputs/answers. P2 artifacts project **all** items associated with the Paper, reachable concepts, relations whose two endpoints are reachable, provenance for those items/relations, documents for those locators, plus output links and candidates. Arrays are ordered by UUID; associations by tuple of IDs. Items: id/type/title/body/origin/confidence/lifecycle/attributes/revision; concepts add preferredName/normalizedName/domain/aliases in order; relations: id/source/target/type/context/justification/origin/confidence/lifecycle/revision; provenance: id/documentId/pageIndex/pageLabel/section/quoteText/locator/capturedDocumentHash/locatorState/revision; documents: id/status/sha256. Associations include paper/item phaseCode, selectedForP3/priority/rationale, item/concept, item/provenance, and relation/provenance. No paths or timestamps. Archived entities are projected to detect changes/preserve history, but do not satisfy a current output link. Pending provenance is not omitted, and validating it is not required to mark the map processed. A shared entity affects every Paper whose snapshot reaches it.

The shortened names in the internal projection correspond to existing attributes: type=typeCode, body=bodyText, source=sourceItemId, target=targetItemId, context=contextText, and justification=justificationText. They add no DTO fields or reinterpret content; the implementation preserves this mapping when serializing the snapshot.

**Phase editing (ADR-020):** for a new request, savePhaseAnswer on NOT_STARTED returns GateBlocked without an answer, clock/context change, success audit, or new receipt. Saving does not start a phase. An already-started phase may be edited even when it is not active, without re-accepting its chain or changing activePhaseCode: response CAS, no-op, and invalidation follow their existing rules. Durable replay is resolved before this guard; lifecycle and capability restrictions still apply (P2 is unavailable in T04).

First answer write: expectedRevision=0 only when no row exists; new revision=1. Later writes compare the **answer** revision and increment it on an effective change. A stale no-op also returns Conflict; only replay with the same requestId/hash returns the prior result before CAS. A valid no-op preserves answer/phase/Paper revisions, completedAt, and snapshots; it stores a durable receipt without inventing a content-change event.

Phase clocks without a new table/wire field: under IMMEDIATE, obtain M=max(revision) from the Paper's paper_phases. Assign each affected phase the next value M+1, M+2… in PRE/P1/P2 order; do not give several phases the same number. On initialization, PRE=1 active; P1/P2=0 NOT_STARTED. A phase receives a fresh value when its real inputs, state, or active context change; changing context renews the destination phase. Invalidation renews later phases that have started; NOT_STARTED remains untouched. A phase affected several times within one UoW gets one final value. Navigation does not change completedAt/snapshot; invalidation preserves the last completedAt and snapshot as historical acceptance, while state=NEEDS_REVIEW prevents them from appearing current.

advance compares expectedPhaseRevision for fromPhase, requires that it is active, and reevaluates within the TX. Revisions for all service-mutated inputs—relevant PRE metadata, Document, answers, artifacts, and associations—propagate to the clock within their UoW. goBack/touch compares the currently active revision before reading/changing the destination. Replay before CAS preserves idempotency even after the clock advances; rollback consumes no numbers. The maximum remains persisted in rows; phases are not deleted. Use positive integers exactly representable in JSON/TS (up to 2^53−1); overflow is rejected without effects.

advance returns the snapshot/hash of checked inputs; phase and gate.phaseRevision expose the final revision of the completed phase. The hash excludes that revision so it does not change on acceptance. Renewing the destination/context does not invalidate completed phases. External availability changes do not get a fabricated clock: reevaluation blocks if the PDF is missing; the design does not promise to detect an irrelevant external change that does not alter the gate. This policy satisfies monotonic increments/CAS and receipts ([DATA.md](DATA.md)) without requiring local +1 increments that CONTRACTS does not specify.

## Context and lifecycle

Import/upgrade initializes PRE IN_PROGRESS, P1/P2 NOT_STARTED, active PRE, without completion or auto-generating review_type. Upgrade preserves UUID/metadata/document/lifecycle/archivedFrom and bibliographic revision/updatedAt; it only adds processing and context. It does not restore archived Papers. NEW→ACTIVE occurs **on the first successful PRE advance** with Paper.revision/updatedAt and audit in the same TX; editing/navigating PRE, import/upgrade, and opening the reader do not cause it. PRE drafts for a NEW Paper are retained and editable; NEW describes editorial state while the phase may be IN_PROGRESS. P1 therefore sees an ACTIVE Paper. Global COMPLETED is not assigned in v0.1.

P1 continue activates P2: if NOT_STARTED, it starts IN_PROGRESS; if it already has data/NEEDS_REVIEW, that data is preserved. light_read keeps active P1, lifecycle ACTIVE, and nextPhase=null; archive keeps active P1, completes P1, and archives the Paper with archivedFromLifecycle and audit in the same TX, nextPhase=null. Existing P2 is not reset: “remains NOT_STARTED” describes only a path that has never started it. After editing P1, its state is preserved as NEEDS_REVIEW, even if the new decision does not enable P2. Items/concepts/documents are not archived by cascade. Reading archived Papers is allowed; Workflow mutations require an explicit restore through Library. Restore only recovers the previous lifecycle and data/context; it does not execute decisions or complete phases ([DOMAIN.md](DOMAIN.md); [CONTRACTS.md](CONTRACTS.md); TASK02_PORTS:108).

**Reserved COMPLETED:** it is not assigned in v0.1. If the known enum appears, upgrade preserves lifecycle/archivedFrom/UUID and bibliographic revisions; get/read and Library archive/restore preserve the state. Incompatible Workflow transitions return UnsupportedCapability with a safe explanation and no effects. There is no special migration or automatic conversion to ACTIVE, including when restoring ARCHIVED from COMPLETED. After restore, a saved P1 archive decision is not executed without a new human advance.

## Navigation and transaction composition

“Context only” preserves answers/state/completedAt/accepted snapshot and may renew the destination phase revision. goBack does not start NOT_STARTED; touch only initializes/activates forward when enablement rules are met. Reading an already-started phase does not accept prerequisites. A context no-op preserves the clock. Completing P2 keeps active P2 and Paper ACTIVE, with nextPhase=null; it does not invoke P3/P4.

P1 archive uses transactional Library reads of Paper/Document and the application archive_in_tx with a borrowed Transaction. LibraryRepository is in application/library_ports.rs and helpers in application/library.rs, TASK02_PORTS resolution 7. Workflow owns the UoW/receipt; snapshot/state/context/history plus archive/audit/Paper revision commit together. No nested actor, commit, Library receipt, or public archivePaper wrapper. Ownership of admitted work follows ADR-016. Concrete signatures are fixed after T02/T03 are integrated; do not preempt the ABI.

## Required behavior verification

In addition to the T04/T06 brief tests:

- PRE IN_PROGRESS with a sufficient gate: touch(P1) does not start P1 or change NEW; advance(PRE) accepts the snapshot and changes Paper to ACTIVE; touch(P1) is then allowed.
- P1 not accepted/NEEDS_REVIEW: touch(P2) does not start a new phase and advance(P2) does not complete it until the chain is reconfirmed. Reading existing P2 data preserves it without implicit acceptance.
- PRE/P1 accepted and synthetic PDF inaccessible without a DB mutation: later evaluate/advance is blocked, available=false, and current hash differs; the accepted snapshot remains intact with no phase/lifecycle/success-receipt write. Restoring access allows reevaluation. A DB Document change between proof/TX is rejected and its UoW invalidates/renews CAS.
- Bibliographic default unknown does not close PRE without an answer; explained UNKNOWN with matching metadata passes. Metadata changed between preview/advance produces Conflict. P1 decision PENDING/null does not archive.
- A normalized no-op preserves revisions/timestamps/snapshot; stale no-op returns Conflict; replay before CAS does not repeat context. Navigation PRE→P1→PRE uses fresh tokens. Equal revisions on inactive phases do not accept an obsolete active expectation; interleaved answer/artifact changes and context/advance serialize; rollback does not change the persisted maximum.
- Continue→P2→back→edit P1→light_read preserves P2 NEEDS_REVIEW. Archive/restore preserves context, answers, snapshot, and global content without archiving again on restore.
- Justified absence with zero artifacts for every type; invalid IDs block even with an explanation; persisted/queryable links, synthesis, references, relations, and provenance; editing a shared artifact invalidates every Paper reached by the snapshot.
- Saving zero candidates without a fictitious item and setP3Candidate use one justification; a real change increments answer.revision and the P2 clock together. A missing required resolver returns UnsupportedCapability, not false/completed due to absence.
- COMPLETED and ARCHIVED-from-COMPLETED fixtures: upgrade/get/read/archive/restore preserve state; incompatible Workflow transitions return UnsupportedCapability with no effects or normalization.

T04 demonstrates PRE/P1 and progressive P2 pin/unavailability. T06 integrates resolvers; final P2 acceptance waits for T07. Documentary checks of payload/hash do not replace behavior, reopening, IPC, installation, or real access tests.

## Shared P2 scope (ADR-022)

Seeds: all paper_items for the Paper. Follow item_concepts from every reached item, including Concepts used as items, to a UUID fixed point (cycles terminate). Include Relations only if both endpoints are reached; never expand the set through a relation. Insight.affectedConceptIds uses the explicitly linked subset. Keep archived entities and provenance/documents for reached entities as described in the projection above.

affected_papers must invert exactly this closure, including archived/NOT_STARTED Papers; union before/after and invalidate once per Paper, with the helper deciding state/clock. A shared Concept reaches Papers transitively. Editing an external relation endpoint does not invalidate a Paper that does not reach it. Editing a candidate's body/confidence changes the artifact/P2 clock, not the candidate PhaseAnswer if selection/count/justification stay the same. Capturing an associated P2 item does not start a NOT_STARTED phase.

## Candidate editing decisions (ADR-023)

PENDING/null is an unjustified draft; a present object must always be complete/checked. An absence justification contains 1..5,000 characters and is canonically non-empty. T06 does not allow partial saves by key: capture/candidates are available, while formal P2 processing waits for T07. No fictitious item or automatic interpretation of PRE.
