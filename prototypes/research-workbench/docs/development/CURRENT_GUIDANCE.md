## Codex instructions and configuration

Codex builds its instructions from the user home and project root down to the current working directory. At each level, `AGENTS.override.md` takes precedence over `AGENTS.md`, and more specific instructions are applied later. The documentation states a default combined limit of 32 KiB. In this project, AGENTS files contain concise rules and point to the architecture documents and task brief; workers read those documents explicitly. Do not change the global home configuration or the limit for this project. Source: [official AGENTS.md documentation](https://learn.chatgpt.com/docs/agent-configuration/agents-md).

The official configuration uses `[agents]`, `enabled`, `default_subagent_model`, `default_subagent_reasoning_effort`, and `max_concurrent_threads_per_session`. The latter excludes the main thread; `max_threads` is a legacy alias. Roles can reference `config_file` and describe their responsibilities. Role configuration and spawn overrides affect how the model and reasoning effort are resolved. Do not infer the effective model from defaults alone: check the configuration and the spawn or session evidence. Sources: [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference) and [subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents).

The project convention is Sol as coordinator and Luna for narrowly scoped implementation. The coordinator may explicitly assign a complex integration task to a Sol worker while keeping Luna as the default. The documentation recommends Sol for demanding, multi-step work and Luna for clear, bounded tasks. Delegating work does not create Git isolation: assign each worker paths, ownership, and a worktree. Do not edit global configuration or install frameworks or SDKs globally. Source: [model and role selection](https://learn.chatgpt.com/docs/agent-configuration/subagents).

## Worktrees and ownership

Git worktrees provide multiple checkouts with independent branches that share one repository. Before creating or reusing a worktree, check `git status --short`, `git worktree list --porcelain`, the baseline SHA, the branch, and the paths. Use the managed worktree tool when it recognizes the repository; otherwise, use Git CLI as a documented fallback. Do not share branches or assume that isolated checkouts prevent conflicts in shared files. Do not manually delete a directory during cleanup: preserve its changes and report, and remove only a clean worktree that has already been integrated. Source: [official git-worktree documentation](https://git-scm.com/docs/git-worktree).

Sol decides sequencing, freezes, and reassignment of shared files. During execution, the software development workflow assigns code integration to an explicit worker, who reviews the result; the coordinating thread does not write product code. Workers preserve other people’s changes, do not redefine contracts, and stay within their assigned ownership. Local commits and merges follow Sol’s authorized protocol. Pushes, publication, and other remote changes are not allowed by default. A worker’s report closes its technical task; it does not certify the product gate.

## SPEC → contract → task → test

Spec Kit separates requirements, technical planning, tasks, consistency analysis, and implementation or convergence. A requirements checklist and evidence of implementation are different artifacts. The project adopts this documentary separation without installing Spec Kit or duplicating the architecture in another system. Each task starts from a contract and baseline, produces the specified files, APIs, and tests, and ends with a review. Source: [official Agentic SDD reference for Spec Kit](https://github.github.com/spec-kit/reference/agentic-sdd.html).

Superpowers describes design, worktrees, planning, execution, testing, and review as a workflow. The locally installed skill governs the details of how that skill is used. Upstream documentation may advance beyond the installed cache; do not assume version equivalence or reinstall it for this work. Continue work under the existing authorization; ask about permission only when a specific, applicable reason requires it. Source: [official Superpowers repository](https://github.com/obra/superpowers).

## Integration and delivery evidence

Before integrating each task, confirm that its contract and ownership have not drifted, affected tests pass, and the required Rust, TypeScript, general, and security reviews have actually taken place. Then run the composition and IPC checks. Report exact commands, exit codes, fixtures, commits, and evidence classified as `automated`, `manual`, `simulated`, or `pending`. Regenerate and verify DTOs and fixtures; do not maintain duplicate type definitions by hand.

To demonstrate an installed, offline Windows build, use the exact NSIS artifact and SHA in a clean environment without development tools or WebView2. Verify continuity, upgrade, backup, migration, uninstall, reinstall, and finally the PRE–P2 flow and v0.1 portability. Mocks, a build, or an executable from the checkout do not satisfy this gate. If a clean environment is unavailable, continue independent work and leave the gate pending; do not lower the criterion or claim installation has been verified. Project criteria: `docs/architecture/QUALITY.md` and SPEC-001.
