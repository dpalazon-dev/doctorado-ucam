# Managed files and supported Windows operations

T02 ruling, 2026-10-02, ADR-016. It addresses gaps found in the 45c4c8c review; it does not certify that the implementation is complete.

## Ownership and access

Matching hashes do not prove ownership. Records must belong to the active library, use canonical IDs, and use the exact namespace derived from the operation or document. Before issuing a cleanup plan, persistence checks that the resource is not referenced by a current document or another intent. Any discrepancy is retained as an incident.

Composition supplies DocumentStore with both the bound root and `expected_library_id` from `actor.info().library_id`; both values come from the same actor. They are private and immutable. Record identity is compared with this active identity. The manifest is not reread, and an ID supplied by the UI is not accepted as authorization.

DocumentStore centralizes Windows protection in a private adapter. It retains handles to the file and the directory chain needed to prevent the path from being replaced during an operation. It verifies reparse attributes, identity, and the final path beneath the authorized root. Verification must not end with a `PathBuf` that is reopened without protection. The same verified handle is used to read, hash, probe, and mark a file for deletion. Promotion never atomically replaces an existing destination, including one that appears after a preliminary check.

`windows-sys = "=0.61.2"` is authorized as a direct Windows dependency. This version is already present in `Cargo.lock`; only the minimum `Foundation` and `Storage_FileSystem` features are used. The assigned file is `adapters/windows/managed_files.rs`, along with its export and tests. This adds no IPC or frontend access. FFI calls are encapsulated in safe functions with RAII handles, aligned buffers, and checked lengths. Each `unsafe` block documents its invariants. This does not authorize mmap or unsafe code in the PDF parser. If a guarantee cannot be established, return a safe error and retain the resource.

`LibraryRoot::at` retains the location specification without performing I/O. When the actor starts, it binds the existing root once and retains its identity and guards before probing or opening SQLite. A new root is created with protected parent directories and then bound. The handshake shares that same bound root with composition and DocumentStore through an internal actor accessor. It does not resolve the environment variable again or authorize another root from Store. Store rejects an unbound root. Acquiring guards on an existing root creates no resources and does not change the diagnostic path for a future schema; that path still acquires no writer lock and adds no migration, staging, or manifest.

The concrete solution uses the sharing controls and open flags in [OpenOptionsExt](https://doc.rust-lang.org/std/os/windows/fs/trait.OpenOptionsExt.html), checks the opened object with [GetFinalPathNameByHandleW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew), and operates on that handle with [SetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle). For promotion, [FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info) can reject an existing destination with `ReplaceIfExists=false`. Retaining stable parent directories is part of the project decision: checking only the final handle does not protect an earlier open through a replaceable path.

The payload is synchronized before promotion, and the durable intent allows state reconciliation after a restart. Sync failures are never hidden as success. If Windows offers no applicable directory barrier, document that limitation rather than ignoring its result or claiming durability after power loss. Restart tests do not certify hardware or power-loss behavior.

## Operation lifecycle

Promotion may use `FileRenameInfo` with `RootDirectory=null` and an absolute destination derived from the parent whose final path has been verified. The parent chain remains held and protected until the operation ends; `ReplaceIfExists=false` preserves atomic exclusion. The guarantee depends on these guards, not on `RootDirectory` being non-null. The tested relative variant returned Windows error 87; do not generalize that result to every possible API invocation. Parent replacement and destination appearance must be tested without losing bytes.

The accessor `pub fn DbActor::library_root(&self) -> &LibraryRoot` is a read-only Rust interface, also available to integration tests outside the crate. It shares the already bound root and its guards. It cannot reauthorize the root and is not an IPC command.

An admitted Library mutation becomes an application job that owns the entire saga, its maintenance permits, and its `requestId`/token exclusions. The caller waits for the result; dropping the caller neither aborts nor releases the admitted job. Do not expose an `AbortHandle` or introduce a generic scheduler or executor. An owned Tokio task and the existing `JoinHandle` result channel may be used. Shutdown waits for the owner to reach a terminal or recoverable state before closing the actor or releasing the lock.

Before opening a picker, copying, promoting, or cleaning up, acquire the `requestId` exclusion and check the command, payload, and receipt. A compatible request waits and replays its result; an incompatible request fails before external effects. Acquire locks in a consistent order: `requestId` before token. Release or prune exclusion records without allowing two owners for the same key. Do not modify `0001` or keep a transaction open during filesystem operations.

## Recovery and diagnostics

Before cleanup, cancellation, and recovery, validate the plan in a short transaction: check the current row, state, identity, and namespace, and confirm that no document or other intent references the resource. The internal method `LibraryPersistence.validate_cleanup_plan(&CancelPlan)` is permitted to share this check. The owning job retains its exclusions until filesystem work ends; it does not keep the transaction open during I/O. Startup recovery finishes before mutations are admitted. Reject a stale plan while retaining the resource.

The safe recovery result, including global failures, is retained in application state and exposed through Settings. `recoveryRequired` combines this state with durable pending work, including `COMMITTED` records whose resource is missing or ambiguous. An isolated incident does not prevent work with unrelated papers. If global enumeration or reconciliation fails and a safe state cannot be established, Library rejects new mutations until a successful restart and reconciliation. Settings remains available to show diagnostics. No IPC fields or commands are added.

Cleanup can be marked `DONE` only with proof of unambiguous absence or deletion. Failures and resources of uncertain ownership remain `PENDING` with an incident, including when staging failed before producing a hash. Recovery’s `reuseExisting` path applies the same verified cleanup as the normal path. Never fill in proof of cleanup from a generic error.

Correction 2: the internal staging result retains the error and cleanup proof as separate data. In `error_json`, the internal variant `{version:1,kind:"stageFailure",code:<safe ErrorCode>,cleanup:"PENDING"|"DONE"}` is permitted without a migration or IPC change. Only verified absence or deletion permits `FAILED`/`DONE`; a PDF rejection must not be turned into a human cancellation. Recovery may reconcile pending work using the same ownership and absence checks. A persistence failure retains a recoverable diagnostic and is never presented as a successful import.

Inspection, promotion, and cleanup hashes use streaming with a small fixed buffer over the same handle. The complete snapshot is reserved exclusively for the parser, subject to its gate. All Library mutations, including metadata and archive/restore, participate in global `requestId` exclusion before effects or receipts are produced.

F10 ruling: Windows sharing does not restrict `FILE_WRITE_ATTRIBUTES`. [WINDOWS_DIRECTORY_GUARDS](WINDOWS_DIRECTORY_GUARDS.md) specifies relative acquisition, keeping a directory non-empty with a retained child, handle revalidation, startup without writes for a future schema, and internal pins. Its rules supersede the initial description of guards based only on sharing. An absolute destination is allowed only after this full protection has been acquired; implementation and review remain pending.

## Required regression tests

Deterministic synthetic tests must cover: parent or file replacement and destination appearance between validation and operation; current references despite a matching hash; a dropped caller while filesystem work continues; two requests with the same `requestId` and compatible or incompatible payloads; cleanup failure and global recovery failure; and `COMMITTED` with no resource. Tests must not use personal libraries or require changes to global configuration.

## C1 — cancellation of the caller’s own promoted destination

A human cancellation may remove an import’s reserved destination when the import is rejected after detecting a late duplicate. Authorization requires a durable prior `PROMOTED` state and a complete `ConfirmIntent` version 1, with `reuseExisting` false and the IDs, payload, and hash bound to one another. When `prepare_cancel` moves the item to `FAILED`, it preserves `promotionConfirmed:true` in the cancellation `error_json`; otherwise the field is false or absent. Retries of that cancellation preserve and revalidate the value. Never infer it from the file, hash, or path being present.

Transactional validation requires the current library, namespace, IDs, and record; no successful confirmation result or receipt; and zero document references or other intents pointing to the resources. Store may handle only this authorized destination. It checks hash and size on the same handle with parent guards and pins retained, and requires staging to be absent when the destination exists. A destination in `STAGING`, both files present, unknown JSON, a foreign or referenced resource, or any discrepancy must be preserved as ambiguous. A matching hash alone does not establish ownership.

Cleanup removes only the declared `original.pdf`; it retains pins and directories. Confirm `DONE` and the cancellation receipt only after verifying that both declared paths are absent. Already verified absence is idempotent; a deletion failure leaves the item `PENDING` and retains the resource. Test cancellation and replay after a real post-promotion race, reopening a `PENDING` cancellation, and negative controls without durable promotion or with a current reference. This is an internal clarification of C1/ADR-016; it adds no migration, DTO, or IPC command.
